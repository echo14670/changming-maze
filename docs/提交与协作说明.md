## 1. 分支模型（所有 PR 直接进 main）

> 2026-11-20 起取消 `dev` 集成分支，采用 trunk-based：`main` 是唯一长期分支，所有功能 PR 直接以 `main` 为 base。

| 分支 | 用途 | 谁能推 |
| --- | --- | --- |
| `main` | 唯一长期分支；可运行、可答辩的版本 | 全员通过 PR；管理员紧急时可绕过 |
| `feat/<成员>-<模块>` | 单人功能分支 | 本人 |
| `fix/<模块>-<问题>` | 修 bug | 本人 |
| `docs/<主题>` | 文档、接口说明 | 本人 |
| `test/<模块>` | 测试与回归 | 本人 |

示例：`feat/wang-maze`、`fix/render-shadow-acne`、`docs/api`。

**硬规则**：

- 所有 PR 的 base 都是 `main`，不再向 `dev` 开 PR；
- 不直接往 `main` 推代码；管理员紧急绕过必须事后说明；
- 不给 `main` 做 `force push`，不删除 `main`；
- 功能分支合并后删除，保持分支列表干净；
- 每个 PR 必须通过 `build` 检查，并至少 1 个 approve。

## 3. 日常协作流程

### 3.1 第一次拉仓库

**方式 A：已被加为 collaborator（可直接推分支）**

```bash
git clone https://github.com/echo14670/changming-maze.git
cd changming-maze
npm ci
npm run build
```

**方式 B：还没加 collaborator（fork + PR，当前可用）**

1. 在 GitHub 上点 `Fork`，得到 `https://github.com/<你的用户名>/changming-maze`；
2. 克隆自己的 fork，并把 upstream 指回主仓库：

```bash
git clone https://github.com/<你的用户名>/changming-maze.git
cd changming-maze
git remote add upstream https://github.com/echo14670/changming-maze.git
git fetch upstream
npm ci
npm run build
```

之后从 `upstream/main` 开分支，推到自己的 `origin`，再向 `echo14670/changming-maze:main` 开 PR。

### 3.2 每次开发

**有写权限：**

```bash
git switch main
git pull --ff-only

git switch -c feat/wang-maze
# 写代码 / 改文档
npm run build
npm test
# 自测：双击 index.html，控制台零 error

git add src/maze/ docs/
git commit -m "feat(maze): 生成 15×15 DFS 迷宫并合批墙体"
git push -u origin HEAD
```

**走 fork：**

```bash
git fetch upstream
git switch -c feat/wang-maze upstream/main
# 写代码 / 改文档
npm run build
npm test

git add src/maze/ docs/
git commit -m "feat(maze): 生成 15×15 DFS 迷宫并合批墙体"
git push -u origin HEAD
# 在 GitHub 开 PR：base = echo14670/changming-maze:main，head = <你的用户名>:feat/wang-maze
```

然后在 GitHub 上向 `main` 开 PR，填下面的模板。

### 3.3 PR 模板

```markdown
## 做了什么
- 

## 为什么
- 

## 如何测试
- [ ] `npm run build` 通过
- [ ] `file://` 双击可运行，控制台零 error
- [ ] 手动走了一遍相关流程
- [ ] 涉及图形特性时附截图/录屏

## 检查
- [ ] 没有提交 `node_modules/`、`dist/`
- [ ] 新资产已登记 `assets/LICENSES.md`
- [ ] 改了接口的话，`docs/接口文档.md` 已同步
```

### 3.4 评审与合并

- 每个 PR 至少 **1 个 approve**；涉及接口/渲染管线/结局镜头时，组长也要 review；
- 评审人重点看：是否越权改别人模块、是否破坏接口、是否引入未登记资产、是否 `file://` 打不开；
- 合并方式：**Squash merge**，合并后删除功能分支；
- 评审意见未解决前不合并；有争议时群里拉 10 分钟语音，不在 PR 里吵。

### 3.5 冲突处理

```bash
git switch feat/wang-maze
git fetch origin
git merge origin/main
# 解决冲突 → npm run build → 提交
git push
```

不要用 `rebase` 改写已经 push 的共享分支；只在自己的功能分支上处理冲突。

## 4. 提交信息规范

格式：

```
<type>(<scope>): <一句话说明>
```

| type | 用途 | 示例 |
| --- | --- | --- |
| `feat` | 新功能 | `feat(render): 加入灯笼聚光动态阴影` |
| `fix` | 修 bug | `fix(maze): 修复贴墙穿模` |
| `docs` | 文档 | `docs(api): 补充 EndingSequence 控制点` |
| `test` | 测试 | `test: 增加结局镜头回归` |
| `perf` | 性能 | `perf(render): 阴影贴图降到 1024` |
| `refactor` | 重构 | `refactor(ui): 拆分 HUD 和小地图` |
| `chore` | 杂项 | `chore: 初始化仓库结构` |

要求：

- 一条 commit 只做一件事；不要 `update`、`fix bug`、`123` 这种信息；
- scope 用模块名：`engine` / `maze` / `world` / `render` / `game` / `ui` / `audio` / `docs`；
- 改接口的 commit 必须在正文写“影响：谁需要改”；
- 不提交大文件、生成物、个人截图；`dist/` 已在 `.gitignore`；
- 提交前 `git status` 自查，只 `git add` 自己的文件，不用 `git add .` 扫进别人的改动。

## 5. 周集成与版本

每周六 20:00 做一次集成（答辩前最后一周改为 12.04 晚）。所有 PR 已经直接进 `main`，所以集成就是**冻结 `main` + 打 tag**：

1. 全员把手上的 PR 合完（base 都是 `main`），暂停新 PR；
2. 组长跑：

```bash
git switch main
git pull --ff-only
npm ci
npm run build
npm test
```

3. 手动 10 分钟通关：入口 → 3 火种 → 大门 → 结局镜头；
4. 打 tag：

```bash
git tag -a v0.1.0 -m "week 1 integration"
git push origin main --tags
```

5. 在群里发：本周完成、已知问题、下周计划；对应周报同步更新。

版本号：

| 时间 | tag | 目标 |
| --- | --- | --- |
| 第 1 周 | `v0.1.0` | 迷宫可走、灯笼照明、构建链 |
| 第 2 周 | `v0.5.0` | 四区域、三火种、图形特性齐全 |
| 第 3 周 | `v1.0.0` | 结局、性能、答辩版 |

## 6. 代码与资产红线

- 不提交 `node_modules/`、`dist/`、`.env`、个人配置、系统缓存；
- 不提交未授权的模型/贴图/音频；只收 **CC0 / CC BY**，并在 `assets/LICENSES.md` 登记；
- 不提交个人概念图、聊天截图、含学号/身份证/住址的文件；
- 单文件 ≤ 20MB，全部资产 Base64 后 ≤ 20MB；大文件先找组长；
- 运行时不访问网络；three.js 本地打包，不引 CDN；
- 不把 `main` 当实验分支；实验性代码放 `feat/`。
